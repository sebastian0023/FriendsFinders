# Product: Nearby Friends

A serverless backend system enabling real-time location sharing between friends on a mobile app. Opted-in users share their location and see a list of friends who are geographically within a configurable radius (default 5 miles). Each entry shows distance and the timestamp of the last location update. The list refreshes every few seconds.

## Scope: Academic Project

This project is built for academic purposes. Scalability is not a primary concern — the architecture should be correct and well-structured but does not need to handle production-scale traffic.

## Functional Requirements

- Users see nearby friends (within configurable radius, default 5 miles) on their mobile app
- Each nearby friend entry displays: friend profile, straight-line distance, last-updated timestamp
- Location data refreshes every 30 seconds from each active client
- Friends inactive for more than 10 minutes are automatically removed from the nearby list
- Location history is stored persistently for all active users (for future ML use)
- Users can add and remove friends; the nearby list updates accordingly in real time
- Users can opt in or opt out of location sharing (subscribe/unsubscribe)
- On app initialization, the client receives current locations of all nearby online friends immediately
- The nearby radius is configurable (not hardcoded), read from SSM Parameter Store
- Hard cap on friends (configurable, default 5,000 max)
- Users can discover nearby strangers (non-friends within radius) who have opted in to discovery
- Users can toggle discoverability on/off independently from location sharing
- Users can send friend requests to nearby strangers; the recipient can accept or decline
- Each user has a profile with a display name and profile picture
- Profile pictures are uploaded to S3 and served via pre-signed URLs or CloudFront
- Profile picture uploads go through a pre-signed S3 URL generated by the backend

## Non-Functional Requirements

- Low latency: location updates propagate to friends with minimal delay
- Reliability: resilient system; occasional single data-point loss is acceptable
- Eventual consistency: a few seconds of replication lag is acceptable
- No GDPR/CCPA compliance required

## Out of Scope

- Peer-to-peer connections between clients
- Travel distance or routing APIs (Haversine only)
- Strong consistency for location data

## Key Behavior Flows

### 1. WebSocket Connect ($connect)
- Authenticate user from token query param
- Store connectionId → userId mapping in DynamoDB Connections Table
- Fetch user's full friend list from DynamoDB Friendships Table
- Batch-fetch friends' locations from ElastiCache Location Cache (skip inactive)
- Compute Haversine distance; include friends within radius
- Send `init.response` to client with all nearby friends
- Subscribe to all friends' Redis pub/sub channels (active and inactive)
- Publish user's current location to their own Redis pub/sub channel

### 2. Periodic Location Update (location.update)
- Write location record to DynamoDB Location History (fire-and-forget)
- Update ElastiCache Location Cache entry; refresh TTL to 10 minutes
- Publish new location to user's Redis pub/sub channel
- pubsub-fanout Lambda iterates subscribers: compute Haversine, push if within radius, drop if not

### 3. Add Friend (POST /friends/{friendId})
- Write two bidirectional Friendship records to DynamoDB
- Subscribe requester's connection to new friend's Redis pub/sub channel
- Return friend's last known location from cache if active

### 4. Remove Friend (DELETE /friends/{friendId})
- Delete both Friendship records from DynamoDB
- Unsubscribe from removed friend's Redis pub/sub channel

### 5. Opt-in / Opt-out
- Reuses friend.subscribe and friend.unsubscribe flows

### 6. Inactivity / TTL Handling
- Location Cache TTL = 10 minutes; expired key = inactive user
- Inactive users are absent from cache and do not appear in nearby lists
- Every location update refreshes TTL automatically
- No explicit "user went offline" event required

### 7. Nearby Strangers Discovery (GET /nearby-strangers)
- Query all active users from ElastiCache Location Cache within the configured radius
- Exclude the requesting user and all existing friends (lookup Friendships Table)
- Only include users who have opted in to discovery (discoverable flag in Users Table)
- Return list of nearby strangers with: userId, displayName, profilePictureUrl, distanceMiles
- Results are capped to a configurable limit (default 50) to prevent large payloads

### 8. Friend Requests
- POST /friend-requests/{toUserId}: create a pending friend request in DynamoDB FriendRequests Table
- GET /friend-requests: list pending incoming friend requests for the authenticated user
- PUT /friend-requests/{requestId}/accept: accept a request — creates bidirectional Friendship records, deletes the request, triggers subscribe flows
- PUT /friend-requests/{requestId}/decline: decline a request — deletes the request record

### 9. Profile Picture Upload
- GET /users/{userId}/profile-picture-upload-url: generates a pre-signed S3 PUT URL for the client to upload directly to S3
- Client uploads the image to S3 using the pre-signed URL
- On successful upload, client calls PUT /users/{userId}/profile to save the S3 key
- Profile picture URL is resolved to a pre-signed GET URL when serving profile data

## API Contracts

### WebSocket Routes (API Gateway WebSocket)

| Route | Direction | Payload / Action |
|---|---|---|
| `$connect` | Client → Server | Token as query param; returns `init.response` |
| `$disconnect` | Client → Server | Removes connectionId from Connections Table |
| `location.update` | Client → Server | `{ action, latitude, longitude, timestamp }` |
| `friend.subscribe` | Internal trigger | `{ friendId }` — subscribes to Redis channel |
| `friend.unsubscribe` | Internal trigger | `{ friendId }` — unsubscribes from Redis channel |
| `location.push` | Server → Client | `{ type, friendId, latitude, longitude, lastUpdated }` |
| `init.response` | Server → Client | `{ type, friends: [{ friendId, latitude, longitude, lastUpdated, distanceMiles }] }` |

### REST Endpoints (API Gateway HTTP API)

| Method | Path | Description |
|---|---|---|
| POST | `/friends/{friendId}` | Add a friend (triggers subscribe) |
| DELETE | `/friends/{friendId}` | Remove a friend (triggers unsubscribe) |
| GET | `/users/{userId}/profile` | Get user profile (includes pre-signed profile picture URL) |
| PUT | `/users/{userId}/profile` | Update user profile (displayName, profilePictureKey, discoverable) |
| GET | `/users/{userId}/profile-picture-upload-url` | Get pre-signed S3 URL for profile picture upload |
| GET | `/nearby-strangers` | Discover nearby non-friends who are discoverable |
| POST | `/friend-requests/{toUserId}` | Send a friend request |
| GET | `/friend-requests` | List pending incoming friend requests |
| PUT | `/friend-requests/{requestId}/accept` | Accept a friend request |
| PUT | `/friend-requests/{requestId}/decline` | Decline a friend request |

## Constraints and Decisions

- All routing goes through the backend (no P2P)
- Distance is always straight-line Haversine
- Friendships are strictly bidirectional
- Nearby radius must be configurable via SSM/env var
- Inactive friends (TTL expired) are not shown
- All Lambda functions run inside VPC to reach ElastiCache Redis
- AWS SDK v3 (modular) for all AWS service calls
- All infrastructure is Terraform (no CDK, SAM, or Serverless Framework)
- Profile pictures stored in S3 with server-side encryption; accessed via pre-signed URLs
- Nearby strangers discovery only shows users who have explicitly opted in to discoverability
